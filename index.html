02 — Infrastructure

Resilience by design, not by luck.

A validator that depends on one cloud, one region or one machine is a single point of failure. We remove every one of them we can.

Multi-cloud

Fleets are deployed across AWS, Google Cloud and Microsoft Azure in separate accounts with separate credentials, quotas and billing. A provider-wide incident degrades a fraction of the fleet, never all of it.

  • AWS
  • Google Cloud
  • Azure

Geographic diversity

Nodes run across North America, Europe and Asia-Pacific, in independent regions and availability zones. Regional outages, network partitions and local power events stay local.

  • N. Virginia
  • Frankfurt
  • London
  • Singapore
  • Tokyo

Distributed validators

On Ethereum we run validators as distributed validator clusters: the key is split across independent nodes and signing requires a threshold. No single machine holds a full key, and the loss of a node costs nothing.

  • Threshold signing
  • No single key
  • Fault tolerant

Key management

Validator keys are generated offline, held in remote signers with slashing protection, and never stored on the host that talks to the network. Access is hardware-backed, least-privilege and logged.

  • Remote signer
  • Slashing protection
  • Hardware-backed access

Distributed validator cluster

One validator. Four machines. Three clouds.

A distributed validator cluster spreads one validator across independent operators, clouds and regions. Any threshold of nodes can sign; any minority can fail. The validator keeps attesting through a cloud outage, a hardware failure or a maintenance window.

03 — Operations

Run like production, because it is.

The chain does not care about intentions. It cares whether the node signed on time. Everything below exists to make that boring.

01

24/7 monitoring and on-call

Prometheus and Grafana on every host. Alerts page a human engineer, day or night, with escalation if unacknowledged.

02

Backups and rehearsed restores

Encrypted snapshots to off-site object storage on a fixed schedule. Restores are rehearsed, timed and documented, not assumed.

03

Staged upgrades

Every client release goes to TestNet first, then rolls through MainNet nodes one at a time. Rollback paths are prepared before anything ships.

04

Hardened hosts

One security group per host, no public inbound, admin access from fixed addresses only, instance metadata locked down, termination protection on.

05

Runbooks and change control

Deploy, join, upgrade, restore and incident procedures are written down, versioned and followed. Every production change leaves a record.

06

Isolated failure domains

Separate cloud accounts, quotas, credentials and backup prefixes per node. One node's incident cannot become another node's incident.
